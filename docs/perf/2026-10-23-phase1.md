# Phase 1 performance measurements (2026-10-23)

## Environment

- Local Mac (Apple M5, macOS 27.0.1), Node v24.18.0, PostgreSQL 16.14 on localhost (trust auth, same machine as the API, so network latency is ~0).
- Database `readiness_coach_perf`, seeded by `npm run seed:perf` (user `perf-user`, 90 days ending today UTC): 28,535 health samples and 51 workouts.
  - `heart_rate` every 5 min (about 25.9k), 6 `hrv_sdnn` and 1 `resting_heart_rate` per day.
  - One staged night per day of about 7 h: 5 cycles of core/deep/core/rem/awake, 25 `sleep_analysis` segments per night (2,250 total). Real HealthKit nights can have fewer or more segments, so the sleep byte counts depend on this choice.
  - 4 workouts per week.
- API run with `npx tsx src/index.ts`, empty `LLM_API_KEY` (template advisor), single process.
- Command: `npm run measure:api -- --base http://127.0.0.1:<port> --token <API_TOKEN> --runs 30`. One warm-up call per endpoint, then 30 sequential timed calls, all with `tz=-240`. Time includes reading the full response body. Bytes are the uncompressed response body.

## Sleep trim gate

Gate: `/v1/sleep?days=90` p95 >= 300 ms or >= 200 KB.

TRIPPED on size: 246,350 bytes (about 241 KiB) is over 200 KB. Latency is well under the limit (p95 54.6 ms). A sleep-timeline task should be added to the plan. Caveat: the size depends on the seeded segment count (25 per night); with the 3-segment nights in `seedDemo.ts` it would be far smaller.

## Server, after

Same database, user, `tz=-240`, 30 runs plus one warm-up, same command; API on `127.0.0.1:4123`, template advisor, single process. Delta is after minus before (p95 and bytes).

| endpoint | p50 ms | p95 ms | bytes | p95 delta ms | bytes delta |
| --- | ---: | ---: | ---: | ---: | ---: |
| /v1/today | 9.3 | 11.4 | 2166 | +3.7 | +707 |
| /v1/body?days=30 | 38.3 | 41.5 | 8628 | -0.4 | 0 |
| /v1/sleep?days=7 | 3.5 | 4.3 | 19381 | +0.7 | 0 |
| /v1/sleep?days=30 | 10.7 | 12.0 | 83000 | +1.3 | 0 |
| /v1/sleep?days=90 | 54.5 | 60.2 | 246350 | +5.6 | 0 |
| /v1/train?days=28 | 24.0 | 25.5 | 3692 | +1.8 | 0 |
| /v1/history?days=30 | 4.0 | 4.2 | 3883 | +0.2 | 0 |
| /v1/history?days=90 | 4.5 | 6.6 | 11584 | +2.0 | 0 |

Targets: every read endpoint p95 < 300 ms (met; the slowest is `/v1/sleep?days=90` at 60.2 ms) and `/v1/body?days=30` < 50 KB (met; 8,628 bytes).

Honest reading of the deltas: the server did not get faster, and it was never the bottleneck (all endpoints were far under 300 ms before). Other than `/v1/today`, the changes are small in absolute terms; independent repeated runs were not collected to establish their significance (the harness has no ETag revalidation, so 304 savings are not visible here).

- `/v1/today` now carries `baselines`, which adds 707 bytes (1,459 to 2,166, +48%). Its p95 rose from 7.7 to 11.4 ms because its sleep query now reads 31 nights (the baseline window); the split between the two causes was not isolated. Both are small in absolute terms and are the cost of letting the app render baselines from the Today response without extra calls.

## App, before

Build: Debug, this branch plus signposts only (no behavior change). iPhone 17 Pro simulator (iOS 26.5) talking to `ios/Fixtures/server.mjs` with `FIXTURE_SCENARIO=normal FIXTURE_LATENCY_MS=250`, so every request costs 250 ms plus near-zero compute. Numbers come from `perf <name> <ms>ms` lines read with `log stream`. Simulator numbers are relative, not phone numbers.

What the intervals mean: `LaunchToToday` runs from `ReadinessCoachApp.init` (pre-main time is not included) to the first moment Today shows a score. `TabSwitch.<tab>` runs from the selection change to the first moment that tab shows data or an empty/error state instead of a spinner.

### Cold launch to Today (median of 5, process terminated between runs)

| case | runs ms | median ms |
| --- | --- | ---: |
| no cached Today on disk (first run, waits on /v1/today) | 494.3, 500.9, 523.2, 526.8, 529.5 | 523.2 |
| cached Today on disk (normal relaunch, stale content shows immediately) | 168.0, 168.3, 168.4, 169.6, 170.5 | 168.4 |

The no-cache case measures first fresh content and takes about twice the configured 250 ms fixture delay. The individual contributions to that interval were not profiled. The cached case only measures how fast stale content paints.

### Tab switches (11 switches into each tab, one every 1.2 s)

| tab | first visit ms | median of all 11 ms | median of 10 revisits ms |
| --- | ---: | ---: | ---: |
| Recovery | 344.0 | 51.1 | 51.1 |
| Sleep | 336.9 | 52.4 | 52.2 |
| Train | 369.3 | 52.8 | 52.8 |
| Today (33 switches back) | 34.1 | 55.0 | 55.1 |

A first visit costs one request (about 250 ms latency plus roughly 90 to 120 ms of view creation and decode). Revisits show the retained response at once (about one frame) and refetch in the background, so the median of 10 switches mostly measures that retained content, not network time. The first visit is the number the later caching work has to beat.

Method at the time of the baseline: the simulator had no configured tap automation (Simulator.app is not scriptable here, and `idb` is not installed). The switches were driven by a temporary timer that set `tabs.selection` in a local build, which goes through the same `TabRouter` path as a tap. That timer was removed before commit; the committed app contains no automation. Real taps would add roughly one frame of input latency that is not measured.

## App, after

Build: Debug, this branch (cached tab prefetch, AppStore, request changes) plus the same temporary `tabs.selection` timer used for the before run. Same simulator (iPhone 17 Pro, iOS 26.5), same fixture (`FIXTURE_SCENARIO=normal FIXTURE_LATENCY_MS=250`), same `log stream` reading of `perf <name> <ms>ms`. The app was terminated with `xcrun simctl terminate` before every launch. The "no cache" runs reinstalled the app first so the disk cache was empty. Simulator numbers are relative, not phone numbers.

### Cold launch to Today (median of 5, process terminated between runs)

| case | runs ms | median ms | before median ms |
| --- | --- | ---: | ---: |
| no cached Today on disk | 552.6, 553.7, 555.0, 581.9, 594.9 | 555.0 | 523.2 |
| cached Today on disk | 179.8, 181.4, 181.5, 183.7, 203.8 | 181.5 | 168.4 |

Cold launch to cached Today is 181.5 ms, under the 1 s target. Both launch medians are slightly slower than before (+32 ms no cache, +13 ms cached, 6% and 8%). The first fresh content still takes about twice the configured 250 ms fixture delay, so this phase did not shorten that path; the extra time is plausibly the store and prefetch setup in `init`, but that was not isolated. Phase 1 did not target the launch path, so this is recorded, not chased.

### Tab switches (11 switches into each tab, one every 1.2 s, started 5 s after launch, cached relaunch)

| tab | first visit ms | median of all 11 ms | median of 10 revisits ms | before first visit ms |
| --- | ---: | ---: | ---: | ---: |
| Recovery | 64.8 | 25.7 | 25.6 | 344.0 |
| Sleep | 37.7 | 38.5 | 38.5 | 336.9 |
| Train | 47.9 | 37.2 | 37.1 | 369.3 |
| Today (33 switches back) | 35.8 | 40.6 | 40.8 | 34.1 |

Same run from an empty disk cache (reinstalled, so the pillar data came only from the Today-triggered prefetch within the first 5 s): first visits 58.9 ms (Recovery), 66.1 ms (Sleep), 47.0 ms (Train); that launch to Today was 524.1 ms.

The recorded first visits are 38 to 66 ms against 337 to 369 ms before. These signposts measure selection-to-content readiness, not a pixel-present timestamp. Every recorded interval is under the 100 ms target. The timer runs were sequential before and after, rather than interleaved, so their ratios are directional evidence, not a controlled speedup estimate.

Method: identical to the before run. The same temporary timer set `tabs.selection` (through `TabRouter`, same path as a tap) in a local build, switching to each pillar tab then back to Today, 11 times per tab. The timer was removed before commit; `git diff` shows no automation in the committed app. Real taps would add about one frame of input latency that is not measured.

## Fixes not shipped

- SQL body aggregation skipped: `/v1/body?days=30` p95 is 41.9 ms (41.5 ms after) at 8.6 KB, already under the 300 ms and 50 KB targets. Revisit with Family Host timing logs.
- `getToday` memo skipped: `/v1/today` p95 is 7.7 ms (11.4 ms after), and the LLM advisor already runs at most once per user per day.
- No sleep timeline trim: only the 90-day range is large (246 KB); the prefetch uses 30 days (83 KB), and ETag means each range downloads once per change.

## Completion verification

The committed app was rebuilt without the temporary timer and exercised through the T3 Device panel with agent-device taps. With the normal fixture at 250 ms delay, first selections in that process recorded Recovery 86.7 ms, Sleep 49.0 ms and Train 36.8 ms. Accessibility snapshots showed populated metrics, sleep stages and workout rows. These are one confirmation run per tab, not repeated benchmark medians, and the snapshots do not establish that no transient spinner appeared.

Checks on 2026-10-23: backend TypeScript, 86 unit tests and 13 PostgreSQL integration tests passed; iOS 71 tests passed; web 7 tests and production build passed. The unchanged web dependencies were installed with npm ci to run the CI checks.

Physical-phone airplane-mode cache retention and a full HealthKit sync remain unverified and require Shawn's phone interaction. The simulator's synthetic fixture does not validate HealthKit upload behavior or production latency. Server runs used a local database and template advisor; no production endpoint p95 or end-to-end LLM latency claim is made. The before and after builds are Debug builds.
