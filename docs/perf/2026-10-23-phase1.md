# Phase 1 performance measurements (2026-10-23)

## Environment

- Local Mac (Apple M5, macOS 27.0.1), Node v24.18.0, PostgreSQL 16.14 on localhost (trust auth, same machine as the API, so network latency is ~0).
- Database `readiness_coach_perf`, seeded by `npm run seed:perf` (user `perf-user`, 90 days ending today UTC): 28,535 health samples and 51 workouts.
  - `heart_rate` every 5 min (about 25.9k), 6 `hrv_sdnn` and 1 `resting_heart_rate` per day.
  - One staged night per day of about 7 h: 5 cycles of core/deep/core/rem/awake, 25 `sleep_analysis` segments per night (2,250 total). Real HealthKit nights can have fewer or more segments, so the sleep byte counts depend on this choice.
  - 4 workouts per week.
- API run with `npx tsx src/index.ts`, empty `LLM_API_KEY` (template advisor), single process.
- Command: `npm run measure:api -- --base http://127.0.0.1:<port> --token <API_TOKEN> --runs 30`. One warm-up call per endpoint, then 30 sequential timed calls, all with `tz=-240`. Time includes reading the full response body. Bytes are the uncompressed response body.

## Sleep trim gate

Gate: `/v1/sleep?days=90` p95 >= 300 ms or >= 200 KB.

TRIPPED on size: 246,350 bytes (about 241 KiB) is over 200 KB. Latency is well under the limit (p95 54.6 ms). A sleep-timeline task should be added to the plan. Caveat: the size depends on the seeded segment count (25 per night); with the 3-segment nights in `seedDemo.ts` it would be far smaller.

## App, before

Build: Debug, this branch plus signposts only (no behavior change). iPhone 17 Pro simulator (iOS 26.5) talking to `ios/Fixtures/server.mjs` with `FIXTURE_SCENARIO=normal FIXTURE_LATENCY_MS=250`, so every request costs 250 ms plus near-zero compute. Numbers come from `perf <name> <ms>ms` lines read with `log stream`. Simulator numbers are relative, not phone numbers.

What the intervals mean: `LaunchToToday` runs from `ReadinessCoachApp.init` (pre-main time is not included) to the first moment Today shows a score. `TabSwitch.<tab>` runs from the selection change to the first moment that tab shows data or an empty/error state instead of a spinner.

### Cold launch to Today (median of 5, process terminated between runs)

| case | runs ms | median ms |
| --- | --- | ---: |
| no cached Today on disk (first run, waits on /v1/today) | 494.3, 500.9, 523.2, 526.8, 529.5 | 523.2 |
| cached Today on disk (normal relaunch, stale content shows immediately) | 168.0, 168.3, 168.4, 169.6, 170.5 | 168.4 |

The no-cache case is the honest "first fresh content" number: about 2 x the 250 ms request latency, so the launch path costs two round trips before a score appears. The cached case only measures how fast stale content paints.

### Tab switches (11 switches into each tab, one every 1.2 s)

| tab | first visit ms | median of all 11 ms | median of 10 revisits ms |
| --- | ---: | ---: | ---: |
| Recovery | 344.0 | 51.1 | 51.1 |
| Sleep | 336.9 | 52.4 | 52.2 |
| Train | 369.3 | 52.8 | 52.8 |
| Today (33 switches back) | 34.1 | 55.0 | 55.1 |

A first visit costs one request (about 250 ms latency plus roughly 90 to 120 ms of view creation and decode). Revisits show the retained response at once (about one frame) and refetch in the background, so the median of 10 switches mostly measures that retained content, not network time. The first visit is the number the later caching work has to beat.

Method: the simulator has no tap automation on this machine (Simulator.app is not scriptable here, and `idb` is not installed). The switches were driven by a temporary timer that set `tabs.selection` in a local build, which goes through the same `TabRouter` path as a tap. That timer was removed before commit; the committed app contains no automation. Real taps would add roughly one frame of input latency that is not measured.
